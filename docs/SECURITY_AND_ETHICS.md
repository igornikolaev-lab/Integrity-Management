# Анонімність, безпека та недопущення зловживань

## Реалізовано в MVP

1. **No raw responses at rest:** сервер не створює таблицю індивідуальних анкет. Кожен POST `/api/survey` в одній транзакції збільшує `cohort_totals.n` та `aggregate_answers.n / score_total`. Немає ПІБ, email, IP, токенів респондентів, часу подання чи окремого запису респондента у БД.
2. **k-анонімний поріг 5:** загальна оцінка формується **тільки з груп, де n ≥ 5**. Для менших груп сервер повертає `suppressed: true`, не повертає їх точну кількість і не видає оцінок. Отже, результат прихованої групи не можна отримати відніманням від показаного загального індексу.
3. **Мінімізація логів:** сервер не веде HTTP access logs і не пише на диск анкети. В журналі управлінських дій не фіксуються анонімні подання.
4. **Серверне RBAC:** ролі адміністратора, аналітика, керівника й учасника перевіряються для кожного захищеного API-ендпоїнта. Паролі користувачів у SQLite хешовані PBKDF2-HMAC-SHA256 із випадковою сіллю (в деморежимі облікові дані відомі).
5. **Сесії:** випадкові HttpOnly / SameSite=Strict cookie, захист від несумісних Origin для POST. HTML escaping на клієнті, відсутність сторонніх CDN.
6. **Human in the loop:** автопропозиція не створює завдання автоматично; керівник приймає рішення, задає виконавця та дедлайн; зміни фіксує журнал.
7. **Виключно модельні дані:** початковий seed не містить жодної реальної інформації про ЗСУ чи НУОУ.

## Від чого захищає і чого не гарантує

- Упереджені / соціально бажані відповіді: **сигнал** розходження з контрольним чек-листом, але не математичне доведення правдивості.
- Зловживання індексом: чітке попередження, що це інструмент **розвитку**, а не рейтинг чи санкційний механізм.
- Маленькі групи: поріг k=5; однак група з 5 осіб ще не гарантує статистичної анонімності, якщо сторонній знає розподіл відповідей.
- Відновлення індивідуального внеску з повторюваних публікацій агрегатів: поточний демонстраційний сервер **не забезпечує повного захисту від differencing-атак у часі**, коли спостерігач послідовно читає результат до і після єдиної нової відповіді. У промисловій версії потрібні публікація лише після закриття хвилі, групові батчі, блокування дрібних оновлень та, за потреби, формальні методи захисту приватності.
- Повторні / автоматизовані подання: **не захищено** на MVP, оскільки немає персональних токенів (це компроміс між анонімністю та захистом від накрутки). Промислова версія має застосовувати одноразові blind/split tokens, незалежні від вмісту анкети.
- Доступ із інтернету: **не призначено** для прямого публічного розгортання. Немає TLS, централізованого управління сесіями, SSO, анти-DDoS, повного security hardening, незалежної перевірки захищеності та затвердженої моделі загроз.

## Політика впровадження

Перед експлуатацією у відомчому контурі потрібні: офіційний власник процесу, DPIA/оцінка ризиків, security review, незалежна перевірка анонімності, HTTPS/TLS, SSO/LDAP або інший санкціонований IdP, ротація та аудит доступів, журналювання адміністрування, політика зберігання даних, резервне копіювання, план реагування на інциденти, затверджені методики та рішення уповноважених осіб. Не імпортувати службові чи персональні дані у поточний MVP.

## Етичні обмеження

Система має відображати **обмеження даних, а не рейтинг посадових осіб**. Не виводити результати мікрогруп, не створювати списків «недоброчесних», не використовувати рекомендації для дисциплінарних рішень. Оцінка — підстава для розмови про покращення процесу, а не висновок про винуватість.
